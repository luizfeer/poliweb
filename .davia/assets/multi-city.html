🌎 Arquitetura multi-cidade

O portal foi projetado desde o dia 1 para suportar várias cidades. Carmo do Rio Claro é a cidade-foco do MVP, mas adicionar Capitólio, Guapé ou outra cidade da região é só uma linha em cities + ativar módulos.

Como funciona

  • Tabela cities — registro mestre. Toda entidade do domínio tem city_id FK.
  • Tabela modules — registro global de funcionalidades disponíveis (utilities, tourism, real_estate, businesses, classifieds, community, transparency, ads, events).
  • Tabela city_modules — liga/desliga módulos por cidade, com config jsonb para overrides.
  • RLS sempre filtra por city_id + papel do usuário. Admin de Carmo não toca em Capitólio.

URLs e roteamento

Decisão recomendada: subdomínio por cidade em produção (crc.portal.com.br, capitolio.portal.com.br) com fallback path-based em dev (/crc, /capitolio). Subdomínio melhora SEO local e identidade.

O middleware Next resolve request.headers.host → cities.slug e injeta currentCity no contexto. Fallback: cookie preferred_city.

Adicionar nova cidade — passos

  1. insert into cities (slug, name, state, status) values ('alpinopolis', 'Alpinópolis', 'MG', 'coming_soon');
  2. Inserir bairros em districts
  3. Habilitar módulos em city_modules (qual liga primeiro? geralmente utilities + events + tourism)
  4. Promover um city_admin local em profile_roles
  5. Configurar subdomínio no DNS + Vercel
  6. Mudar cities.status para active quando estiver pronto

Módulos por cidade

Trade-off escolhido: mesma instância Postgres para todas as cidades (não multi-tenant DB-por-cidade). Custo baixo, queries simples, RLS protege isolamento. Quando uma cidade ficar grande demais, dá pra promover pra DB separado depois.
