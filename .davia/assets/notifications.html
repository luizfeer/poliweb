🔔 Sistema de notificações

Inbox + Push + Email para cidadãos, comerciantes e admins, multi-cidade.

Origem única (Postgres) com 3 canais de entrega: in-app, email (Brevo) e push (Expo + Web Push).

Modelo de dados

  • notifications — item visível no painel/inbox (1 linha por destinatário).
  • notification_deliveries — 1 linha por canal (in_app, email, push) com status (pending/sent/failed/skipped).
  • notification_preferences — opt-out por type + profile_id (+ city_id opcional). Default = ativado.
  • device_push_tokens — tokens Expo do app mobile (iOS/Android). 1 por dispositivo.
  • web_push_subscriptions — PushSubscription do navegador (Web Push API, VAPID).

Pipeline de envio

  1. Server Action ou trigger DB chama public.create_notification(...).
  2. Insere 1 row em notifications + 3 rows em notification_deliveries:
    • in_app sempre sent (já está no banco)
    • email pending se p_send_email = true, senão skipped
    • push pending se o user tem destino E preferência permite, senão skipped
  3. Worker email:deliveries processa fila de emails (Brevo).
  4. Worker push:deliveries processa fila de push:
    • Busca device_push_tokens e web_push_subscriptions do destinatário
    • Envia via Expo Push API (iOS+Android) e web-push (browser)
    • Marca sent/failed, deleta token se DeviceNotRegistered

Worker push:deliveries

  • Arquivo: apps/worker/src/jobs/push-deliveries.ts
  • Daemon permanente no PM2 (worker-push-deliveries), polling 5s.
  • Envs obrigatórias: EXPO_ACCESS_TOKEN, VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT.
  • Marca skipped quando o destinatário não tem nenhum token registrado.

UI

  • Web — /painel/notificacoes = inbox/histórico do usuário. Botão Web Push em components/push/WebPushToggle.tsx.
  • Mobile — Mensagens → Avisos (app/inbox/notifications.tsx) = histórico paginado, pull-to-refresh, marca como lida ao abrir.
  • Mobile — Perfil → Notificações (app/(tabs)/perfil/notificacoes.tsx) = preferências por categoria + lista de dispositivos + botão "ativar neste dispositivo".
  • Roteamento inteligente: lib/navigation/smart-route.ts decide nativa vs webview. /painel/notificacoes roteia pra tela nativa de Avisos automaticamente.

Persistência: por que puxar do Supabase

  • Fonte de verdade única — notificação lida no mobile aparece lida no web.
  • RLS já protege — usuário só vê as próprias.
  • Cache local leve resolve perf (cachedJson TTL 60s; pull-to-refresh força reload).
  • Realtime opcional via supabase.channel('notifications').on('postgres_changes', ...) quando quiser ao vivo.
  • Não duplicar offline — risco de divergir entre devices.

Endpoints mobile (Next API)

  • POST /api/mobile/push/register — registra Expo token (chamado no boot do app)
  • GET /api/mobile/push/state — devices + preferências
  • POST /api/mobile/push/preferences — upsert preferência
  • DELETE /api/mobile/push/device/:id — revoga device

Leitura/escrita de notifications no mobile vai DIRETO no Supabase (sem passar pelo Vercel) — RLS protege. Veja apps/mobile/lib/inbox/notifications-feed.ts.

Badge da tab Mensagens

  • useUnreadNotifications() em apps/mobile/lib/inbox/use-unread.ts.
  • Atualiza via: Supabase Realtime (instantâneo) + poll 60s (fallback) + foreground + emitter notifyUnreadChanged().
  • Pra realtime funcionar, habilitar publication: Supabase Dashboard → Database → Replication → tabela notifications → toggle on. Sem isso, polling continua funcionando.

Por que mobile vai direto no Supabase (e não via /api/mobile)

  • 1 hop a menos (mobile → Supabase, em vez de mobile → Vercel → Supabase)
  • Sem deploy Vercel pra mudar query
  • Realtime grátis via supabase.channel(...)
  • RLS já protege — usuário só vê as próprias linhas
  • Endpoints Next ficam só pra coisas que precisam de service_role ou lógica de servidor (ex: push/register, que valida token do user e faz upsert)

Endpoints web

  • POST /api/push/web/subscribe — registra PushSubscription do browser
  • DELETE /api/push/web/subscribe?endpoint=... — desinscreve

Disparar notificação

Server Action / SQL autenticado:

select public.create_notification(
  recipient_id, city_id, 'user', 'lead.received', 'high',
  'Título', 'Corpo', '/painel', null, null, '{}'::jsonb,
  false,
  '{"route": "/inbox/notifications"}'::jsonb
);

Quando rodar via service_role (sem auth.uid()), inserir direto nas tabelas (a função usa auth.uid() pra autorizar).

Tipos de notificação (convenção)

  • lead.received — lead em negócio/imóvel/CidadeViva
  • business.update — aprovação, status de página
  • city.alert — comunicados oficiais
  • events.new — novos eventos
  • classifieds.reply — interesse em classificado

Categorias visíveis ao usuário ficam em NOTIFICATION_CATEGORIES (apps/web/app/api/mobile/push/state/route.ts) — adicione lá pra aparecer nos toggles de preferência.

Troubleshooting

  • Token não salva: cheque env.webBaseUrl no mobile e logs do app (botão "Ativar neste dispositivo" mostra erro real).
  • Push fica failed com "DeviceNotRegistered": token expirou; worker já apaga automaticamente.
  • Web push nada chega: confere se NEXT_PUBLIC_VAPID_PUBLIC_KEY está no Vercel e se sw.js está carregando.
  • iOS sem push: simulador não recebe; precisa dispositivo físico + dev build novo.
  • "no_session" no mobile: bug do secureStorage em lib/supabase.ts — fix em vigor desde 2026-05-21.
